===============================================================================
                    PARAMETER EXPLANATIONS
===============================================================================

--chunked-prefill-size 32768
    Size of prefill chunks. Larger values reduce CPU scheduling overhead
    but may increase memory pressure. Your data shows 32768 is optimal.

--max-mamba-cache-size 32
    Size of Mamba/SSM state cache. Your best run used 32.

--num-continuous-decode-steps 4
    Run multiple decode steps between scheduler calls.
    - 1 (default): Max flexibility, max scheduler overhead
    - 2-4: Sweet spot for throughput
    - 5+: May increase TTFT

--schedule-policy lpm
    Request scheduling algorithm:
    - fcfs: First-Come-First-Served (default)
    - lpm: Longest Pending Match (better for mixed workloads)
    - lof: Least Occupancy First (better throughput)
    - dfs-weight: Weighted Depth-First Search
    - priority: Priority-based scheduling

--enable-mixed-chunk
    Allows mixing prefill and decode requests in the same batch.
    Essential for good throughput with mixed workloads.

ROOT CAUSE ANALYSIS: HIGH CONCURRENCY BOTTLENECK
------------------------------------------------------

From code analysis of /opt/eagle/sglang/python/python/sglang/srt/managers/schedule_policy.py:

1. **Policy Fallback at High Concurrency**:
   ```python
   def _determine_active_policy(self, waiting_queue: List[Req]) -> Policy:
       if self.policy == CacheAwarePolicy.LPM and len(waiting_queue) > 128:
           # Turn off the expensive prefix matching and sorting when queue is large.
           return CacheAgnosticPolicy.FCFS
       return self.policy
   ```

   When LPM policy is used and queue > 128 requests, it falls back to FCFS,
   disabling the expensive prefix matching and sorting. This indicates that
   these operations are bottlenecks at high concurrency!

2. **Waiting Queue Iteration** (O(n) complexity):
   ```python
   # Get requests from waiting queue to a new prefill batch
   for req in self.waiting_queue:
       # ... various checks ...
       res = adder.add_one_req(req, ...)
       if res != AddReqResult.CONTINUE:
           # Handle result
   ```

   At 64 concurrent requests, this loop iterates through potentially many requests,
   with multiple checks and operations per request. This is O(n) where n is
   the number of requests in the waiting queue.

3. **Memory Pool Allocation Overhead**:
   - HybridReqToTokenPool and MambaPool require lock-based allocations
   - Each request needs memory allocation and state tracking
   - At high concurrency, lock contention becomes significant

4. **Prefill Request Addition Complexity**:
   ```python
   def add_one_req(self, req: Req, has_chunked_req: bool):
       # Multiple checks and operations:
       # 1. Token calculation
       # 2. Memory availability check
       # 3. Tree cache lookup (if applicable)
       # 4. State updates
       # 5. Sorting insertion (if needed)
   ```

   Each request addition requires multiple operations, and at high concurrency
   the cumulative overhead becomes significant.

WHY EAGLE3 DOESN'T HELP:
----------------------------
EAGLE3 (Speculative Decoding) primarily helps:
- ✅ Decode speed (predicts multiple tokens at once)
- ✅ Single concurrent scenarios (S1)
- ❌ **High concurrency scenarios (Smax)**

EAGLE3's bottleneck is the Draft Model's inference and verification process,
which adds overhead at high concurrency. The main bottleneck in your case
is NOT decode speed, but rather:
1. Request scheduling overhead
2. Memory allocation/management
3. Batch formation complexity
4. Thread synchronization

These are all CPU-side operations that EAGLE3 doesn't help with.
