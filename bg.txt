Arguments:

- At 160K context, L00 prefill attn_kernel = 145ms avg, 389ms max per step

================================================================================
OPINION B: "Naive sparse attention is net-negative on decode"
================================================================================
Claim: Standard sparse attention scoring (compress_k -> Q*KC1 -> topk) reads
the ENTIRE KV cache to compute KC1. This costs as much bandwidth as dense
attention itself. On decode, where dense attention only costs 3.1ms/step for
8 layers, adding scoring overhead of ~30ms/step makes it WORSE.

This is why minicpm_flashinfer (even ignoring INT4 issue) isn't faster than
flashinfer on S1/S8 -- the scoring overhead dominates.

Proposed algorithmic fixes:
1. INCREMENTAL KC1: Only update 1-2 KC1 entries per decode step (not recompute
   all). Each new token affects at most 2 sliding windows. Cost drops from
   7.7MB to 4KB per layer per step (~2000x reduction).
2. CACHE TOPK ACROSS STEPS: Recompute every N=4-8 steps. Topk blocks barely
   change between consecutive tokens. Saves 75-87% of scoring.
3. SHARE TOPK ACROSS LAYERS: Compute at layer 0, reuse for layers 9-31.
   Important blocks are correlated across layers. Saves 7/8 of scoring.
4. REDUCE TOPK (64 -> 32 or 16): Model was trained with topk=64, but inference
   can be more aggressive. Must test accuracy stays >97%.
5. SKIP KC2: Only use KC1 for scoring. At 160K, KC1 is ~10K entries -- manageable.

NOTE: The incremental KC1 concept is sound but minicpm_backend already has
infrastructure for this (history_compress_token_nums, new_compress_token_nums).
However, that infrastructure is in minicpm_backend.py which is NOT used with
the flashinfer backend -- would need to be reimplemented.

================================================================================
Claim: minicpm_flashinfer uses bf16 weights (INT4 breaks accuracy). MLP is

Math:
  MLP with INT4 Marlin: ~204s of 1036s on Smax
  MLP with bf16:        ~816s (4x weight reads)
  Penalty:              +612s
  Max sparse attn save: ~139s
  Net:                  +473s SLOWER

Conclusion: minicpm_flashinfer + bf16 cannot overcome the 4x MLP penalty.
Only viable path is sparse attention ON flashinfer with INT4.

OPINION F: "5 bugs in naive sparse attention implementation"
================================================================================
An AI attempted to implement sparse decode in MiniCPMAttention.forward() and
another AI found these bugs:

1. CUDA graph guard (`not torch.cuda.is_current_stream_capturing()`) disables
   sparse path during CUDA graph capture AND replay -- dead code in production.
2. Gathers ALL keys to decide which keys to read -- same bandwidth as dense.
3. Uses per-block-64 mean instead of strided sliding-window (kernel_size=32,
   stride=16) -- wrong compressed keys, accuracy degrades.
4. Materializes full attention matrix with einsum instead of using FlashAttention.
5. GQA handling assumes num_kv_heads=1, breaks on other configs.

Lesson: implementing sparse attention correctly requires understanding the
exact KC1 compression algorithm and FlashInfer's paged KV cache API.

OPINION H: "Implementation plan for sparse prefill on flashinfer" (AI session 4)
================================================================================
Approved plan being implemented in sglang_sala_flashinfer/:

Architecture:
  MiniCPMAttention.forward() [minicpm.py]
    -> compute KC1 (compress_k Triton kernel) + KC2
    -> score via infllmv2_attn_stage1(q, kc1, kc2) -> topk block indices
    -> attach topk_idx to forward_batch
    -> call self.attn() as normal

  FlashInferAttnBackend.forward_extend() [flashinfer_backend.py]
    -> detect minicpm4 layer (layer_id in {0,9,16,17,22,29,30,31})
    -> if sparse metadata present: build filtered kv_indices from topk blocks
    -> use pre-allocated sparse BatchPrefillWithPagedKVCacheWrapper
    -> call begin_forward() with filtered indices, then forward(), end_forward()
    -> else: use normal dense wrapper (for lightning layers + short sequences)

Key design decisions:
  - Prefill only, no decode changes
  - Only for sequences > dense_len (8192 tokens)
  - Reuses existing compressed_attention() from minicpm_sparse_utils.py
  - Pure torch/Triton block-to-page mapping (no C++ extension dependency)
  - Pre-allocate sparse wrapper in __init__() to avoid per-call overhead
  - Per-query-token topk (each query token picks its own topk blocks)
  - Start with topk=64 (model default), tune down if accuracy holds

Code path traced (confirmed feasible):
  MiniCPMAttention.forward() -> self.attn() -> RadixAttention.forward()
  -> forward_batch.attn_backend.forward() -> FlashInferAttnBackend.forward_extend()
  -> prefill_wrapper_paged.forward(q, kv_buffer)

  Insertion points:
  1. minicpm.py: before self.attn() call (~line 194)
  2. flashinfer_backend.py: in forward_extend() (~line 772), between
     kv_indices construction (line 1376) and begin_forward (line 1427)

Concerns flagged:
  - KV cache save/read: plan says "save k,v to cache first, read back" --
    may cause double write if self.attn() also saves KV internally. Need to
    verify RadixAttention's KV save behavior.
  - Sparse wrapper overhead: FlashInfer begin_forward() has non-trivial cost
    (~0.091ms/layer from profiling). Pre-allocation helps but per-call
    begin_forward still needed with different kv_indices each time.
  - GQA handling: 32 Q heads / 2 KV heads = 16:1 ratio. topk computed per
    KV head group. Must handle correctly.

Files being modified:
  sglang_sala_flashinfer/sglang/srt/models/minicpm.py
  sglang_sala_flashinfer/sglang/srt/layers/attention/flashinfer_backend.py

Files reused as reference:
  minicpm_sparse_utils.py: compressed_attention(), compress_k_core_new()
  minicpm_sparse_kernels.py: compress_k_complete_kernel_new (Triton)
  minicpm_backend.py: sparse page table construction

CRITICAL CORRECTION ON LIGHTNING DECODE (2026-04-07):
  Lightning attention does NOT read the KV cache during decode. It uses a
  fixed-size recurrent state (H=16, K=128, V=128 per layer = 512KB/layer).
  fused_recurrent_simple_gla processes T=1 per decode step:
    1. Load state from MambaPool (128×128 per head per layer)
    2. state = state * exp(g_gamma) + k^T @ v  (rank-1 update)
    3. output = q @ state  (query)
    4. Save updated state
  This is O(1) per token -- does NOT scale with sequence length.
  The 15ms/step cost is from state I/O + matmuls across 24 layers × 16 heads,
  NOT from reading a growing KV cache.

  IMPLICATION: For long-context S8/Smax, lightning is a FIXED COST per step.
  The SCALING bottleneck is minicpm4 dense decode attention (8 layers, O(n)
  per step, reads full KV cache). This makes sparse decode for minicpm4
  layers the highest-impact optimization for S8/Smax.

FLA KERNEL DETAILS (fused_recurrent_fwd_kernel, fla 0.4.1):
  Location: fla.ops.common.fused_recurrent (external pip package)
  Local copy: sglang_sala_flashinfer/_fla_reference/common/fused_recurrent.py
  For simple_gla: USE_G=False, USE_G_GAMMA=True, USE_GK=False, USE_GV=False
  Block sizes: BK = min(next_power_of_2(K), 64) = 64, BV = 64
  NK = ceil(128/64) = 2, NV = ceil(128/64) = 2
  Grid = (NV=2, NK=2, N*H) = 4 blocks per head
  State b_h[BK=64, BV=64] lives in registers during the loop.
  For T=1 decode: loop runs once, then o = o.sum(0) reduces NK=2 partial outputs.
  The BK=64 cap forces NK=2 split + Python-level reduction (extra kernel launch).
  Potential optimization: BK=128 → NK=1, no reduction needed. Needs register
  pressure check (128×64 = 8192 floats = 32KB registers per block).

OPINION D3: "sglang_sala_flashinfer vs minicpm_flashinfer" (2026-04-03)
================================================================================
Why minicpm_flashinfer + INT4 breaks but sglang_sala_flashinfer + INT4 works:

  minicpm_flashinfer backend (BROKEN with INT4):
  - Replaces the ENTIRE attention backend (both prefill and decode)
  - ALL attention (prefill + decode) goes through sparse pipeline
  - Reshapes KV cache by head groups: view(-1, page_size, tp_k_head_num//2, head_dim)
  - Page indices multiplied by 2 + head_group_idx for per-head-group addressing
  - Uses FlashAttention (sgl_kernel.flash_attn) for the actual attention, not FlashInfer
  - Sparse decode on every token → accumulated precision errors over 1000s of steps
  - Custom C++ extension (sparse_kernel_extension) for block table construction
  - Has its own memory pool (MiniCPMReqToTokenPool) with compressed key slots
  - Bottom line: deep custom plumbing that interacts badly with INT4 Marlin

  sglang_sala_flashinfer (WORKS with INT4):
  - Uses the STANDARD FlashInfer backend (FlashInferAttnBackend) for everything
  - Only intercepts the PAGED attention during PREFILL (forward_extend ragged+paged)
  - KV cache layout is UNCHANGED from dense FlashInfer (no head-group reshaping)
  - Decode is 100% dense (standard FlashInfer decode wrapper, no sparse)
  - Model weights go through the SAME Marlin INT4 dequant path as dense
  - Standard memory pool (no compressed key slots in KV pool)
  - Sparse metadata passed via kwargs through RadixAttention → attn_backend.forward()
  - Temporary BatchPrefillWithPagedKVCacheWrapper for sparse paged attention
  - Bottom line: minimal invasive changes, everything else is standard FlashInfer

  Key architectural differences:
  1. SCOPE: minicpm_flashinfer = full backend replacement. sala_flashinfer = prefill-only overlay.
  2. DECODE: minicpm_flashinfer = sparse decode. sala_flashinfer = dense decode.
  3. KV CACHE: minicpm_flashinfer = custom layout with head-group split.
     sala_flashinfer = standard FlashInfer layout.
  4. ATTENTION KERNEL: minicpm_flashinfer = FlashAttention. sala_flashinfer = FlashInfer.
  5. KC1 STORAGE: minicpm_flashinfer = persisted in KV cache pool (Triton kernel writes back).
     sala_flashinfer = module-level Python dict cache (separate from KV pool).
  6. BLOCK TABLE: minicpm_flashinfer = C++ extension (get_block_table_v2).
     sala_flashinfer = Python + torch operations to build filtered kv_indices.

  Why INT4 accuracy is preserved in sala_flashinfer:
  - Dense decode means no accumulated sparse errors over decode steps
  - Standard KV cache layout means no interaction with Marlin dequant
  - The sparse prefill only affects which SUBSET of KV tokens are attended to,
    not HOW the attention is computed (same FlashInfer kernel, same numerics)
  - First dense_len (8192) tokens always included → baseline context preserved

Architecture:
  MiniCPMAttention.forward() computes KC1/KC2 from prefix keys + new keys,
  scores Q against KC1 via infllmv2_attn_stage1, selects topk blocks,
  passes sparse_metadata through kwargs to FlashInfer backend.
  FlashInfer forward_extend() builds filtered kv_indices with only selected
  blocks, runs sparse paged attention via temporary wrapper, merges with
  ragged self-attention via LSE merge.

Bugs found and fixed (3 iterations):

  1. cu_seqlens_q not multiplied by heads_per_group (16) for infllmv2_attn_stage1.
     The scoring kernel expects adjusted seqlens to handle GQA grouping.
     Without this, scoring produced garbage -> topk missed critical blocks.
     Result: 151K multi-doc test got stuck in degenerate loop, never found answer.

  2. max_seqlen_q not adjusted by heads_per_group either. Same root cause.

  3. total_q passed as q.shape[0] instead of -1 (original default) to
     max_pooling_1d_varlen.

  4. First dense_len tokens not guaranteed in filtered kv_indices. Original
     SALA design: always attend to first dense_len (8192) tokens densely,
     apply topk only beyond that. Our implementation initially applied topk
     to the ENTIRE prefix, which could drop early important tokens.
     Fix: always include tokens [0, dense_len) + topk blocks beyond dense_len.

  5. Threshold was prefix_len < dense_len (strict less). With chunked_prefill_size
     = dense_len = 8192, prefix of exactly 8192 triggered sparse incorrectly.
     Fix: changed to prefix_len <= dense_len (must strictly exceed).

  6. KC1 computed from scratch every chunk by reading ALL prefix keys from KV
     cache. Performance fix: skip KC1 for requests with prefix <= dense_len.

  7. Redundant Triton kernel call in flashinfer_backend to build original
     kv_indices before filtering. Fixed by building filtered indices directly
     from req_to_token.

Test results (SGLANG_SPARSE_PREFILL=1, chunked_prefill_size=32768):
  Test 1 - Capital of France (20K tokens):  PASS ("Paris")
  Test 2 - Needle in Haystack (87K tokens): PASS ("BLUE-TIGER-42")
  Test 3 - Multi-document (151K tokens):    PASS ("Alice Zhang, 1987")
  Test 4 - Long Generation (decode):        PASS
  KL divergence: 0.000 (all 5 prompts)
  Correctness: fully preserved vs dense baseline.

Key finding -- chunked_prefill_size matters for sparse accuracy:
  With chunked_prefill_size=8192: Test 2 FAILS (degenerate loop after 4096 tokens).
  With chunked_prefill_size=32768: Test 2 PASSES.
  Reason: each sparse chunk independently selects topk blocks. Smaller chunks
  mean more sparse iterations, and KV cache entries produced under sparse
  attention propagate errors through subsequent layers and chunks. With 8192
  chunk size, Test 2 has ~9 sparse chunks (error compounds). With 32768,
  only ~2 sparse chunks.

Performance assessment:
  No measurable speedup on these test cases. The KC1 computation (reading all
  prefix keys from KV cache + compress + score + topk) adds overhead that
  offsets the savings from reduced paged attention. The original minicpm_backend
  uses incremental KC1 (only new entries per chunk) which avoids this cost.
  To get real speedup, need either:
    a. Incremental KC1 updates (only compute new KC1 entries, cache history)
    b. Much larger sequences where attention savings dominate KC1 overhead
    c. Avoid per-layer temporary FlashInfer wrapper creation

Status: CORRECTNESS VALIDATED, PERFORMANCE NEUTRAL.
  Sparse prefill is working correctly on flashinfer path with W4A16 Marlin.
  No accuracy degradation. But no speed gain yet -- need optimization work
  to reduce KC1 overhead before this translates to competition score improvement.
