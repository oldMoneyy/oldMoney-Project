================================================================================
MODEL: MiniCPM-SALA (~9.48B params, bf16)
================================================================================
- Hybrid architecture: 8 minicpm4 layers (sparse softmax attention, GQA 16:1)
  + 24 lightning-attn layers (linear attention, full MHA)
- minicpm4 layers at positions: 0, 9, 16, 17, 22, 29, 30, 31
- lightning-attn layers: all other positions
- Sparse attention config: window_size=2048, topk=64 blocks, dense_len=8192
- MLP dominates params: 67.98%, attention: 25.67%, embeddings: 6.35%
- Max context: 524,288 tokens (512K)

================================================================================
CURRENT OPTIMIZATION STATUS (What has been tried)
================================================================================

1. QUANTIZATION (DONE, at limit)
   - W4A16 GPTQ for all possible layers (INT4)
   - Only norm, lm_head, embedding kept at bf16
   - This is quantized to its practical limit

2. SPECULATIVE DECODING (TRIED, negligible gain)
   - Helped very little, not worth pursuing further

3. KERNEL FUSION (TRIED, negligible gain)
   - Profiled extensively (see profiling_reference.txt)
   - Only found scale+add+residual kernel fusion, saved ~0.5s on long requests
   - MiniCPM and SGLang experts reviewed profiling, confirmed not much room
     left on the fusion side

4. FLASHINFER vs MINICPM_FLASHINFER BACKEND
   - flashinfer backend: faster on S1 and S8
   - minicpm_flashinfer backend: faster on S64 (high concurrency)
   - BUT minicpm_flashinfer has redundant implementation and CANNOT work with
     INT4 quantization -- accuracy degrades catastrophically
   - Even with dense_len=655360 hack (forcing all inputs to dense attention
     branch), minicpm_flashinfer still cannot maintain accuracy with INT4
   - Lightning MLP INT4 + all other params bf16 = still bad accuracy
   - Decision: ABANDONED minicpm_flashinfer, using flashinfer backend

5. SGLANG ARGS TUNING (TRIED, negligible gain)
   - chunked_prefill_size, torch_compile, max_running_req, etc.
   - Marginal improvements only

PROFILING DATA (W4A16 quantized model, all layers INT4, 64-concurrency bench)

      (all layers INT4, only norm/lm_head/embedding bf16). NOT bf16.

      The performance gap comes from algo/system differences, not quant/backend.

  Prefill: 421s (52%) -- 151 steps x 2.79s/step
  Decode:  403s (48%) -- 38,533 steps x 10.46ms/step

  Prefill 421s breakdown:
    MLP (32 layers):              189s  (45% of prefill)
    MiniCPM4 attn (8 layers):     134s  (32% of prefill)
    Lightning attn (24 layers):    88s  (21% of prefill)
    Other:                         10s  ( 2% of prefill)

  Decode 403s breakdown:
    CUDA graph replay:            377s  (94% of decode)
    Overhead (sched+sample):       26s  ( 6% of decode)

  Per-step prefill bottleneck ranking (W4A16 quantized):
    #1 MLP GEMMs (32 layers x 39ms):        1253ms/step  (49%)
    #2 Lightning GEMMs + fla (24 x 24ms):    582ms/step  (23%)
       (fla kernel alone: 17ms/layer, does NOT benefit from quantization)
    #3 MiniCPM4 GEMMs (qkv+gate+o, 8 layers): 296ms/step (12%)
    #4 MiniCPM4 sparse attn (8 x 28ms):      224ms/step  ( 9%)
    #5 Overhead (norms, gates, launches):    ~200ms/step  ( 8%)

  Sparse attention per-layer breakdown at ~229K context:
    alloc_fill:      0.1ms  (torch.full for compressed K buffers)
    compress_k:      0.2ms  (mean-pool KV -> KC1 and KC2)
    attn+pool+topk: 14.3ms  (infllmv2_attn_stage1 + max_pool + topk, O(n))
    block_table:     3.0ms  (get_block_table_v3, constant)
    page_setup:      1.6ms  (compute seqlens, get KV buffers, constant)
    flash_attn:      9.5ms  (FlashInfer on selected 6144 tokens, constant)
    TOTAL:          ~29ms/layer x 8 layers = 232ms/step

  Decode throughput: ~62.85 tokens/s (~15.9ms per token)

================================================================================
KEY INSIGHT FROM EXPERT MEETING (2026-04-03)
================================================================================
After 1 month of optimization focused on system-level optimizations (fusion,
quantization, backends, args), the MiniCPM expert pointed out:

"We are limiting our imagination because we didn't think about modifying the
algorithm itself."

Suggested direction: ALGORITHMIC MODIFICATIONS to the sparse attention mechanism:
- More aggressive topk (e.g., reducing KC1, KC2 values)
- Topk approximation methods
- Other algorithmic changes to reduce computation while maintaining accuracy

IMPORTANT CONSTRAINT: All competitors use the same flashinfer backend and same
W4A16 quantization. The 35% gap to leader MUST come from algo/system differences.

Sparse attention (134s = 32% of prefill = 17% of total) is NOT the only target.
Even eliminating it entirely only saves 17%. The gap is 35%.

Other potential targets:
- fla kernel for lightning attn: 88s (21% of prefill), non-GEMM, can't be quantized
- MLP GEMMs: 189s (45% of prefill), already W4A16 Marlin -- same for everyone
- Decode phase: 403s (48% of total), mostly CUDA graph replay
