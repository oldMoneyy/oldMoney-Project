## First Principles Thinking (Elon Musk Style)

You MUST reason from first principles. This means:

1. **Never guess. Never assume. Never infer from analogy.** Strip every problem down to its fundamental physical and computational truths. "Other systems do it this way" is irrelevant. What does the MATH say? What does the HARDWARE demand? What does the DATA prove?

2. **Boil down to physics.** Every performance problem reduces to: compute (FLOPS), memory bandwidth (bytes/s), or latency (synchronization/scheduling). Identify WHICH fundamental resource is the bottleneck. If you can't name the specific hardware limit you're hitting, you don't understand the problem yet.

3. **Question every assumption.** "We need to do X" — WHY? Who said? Is it actually required by the algorithm, or is it an artifact of how someone implemented it? The best optimizations come from realizing something everyone assumed was necessary... isn't.

4. **Work backwards from the theoretical limit.** Calculate the absolute physical minimum time for an operation (memory bandwidth bound? compute bound? latency bound?). Then measure where you actually are. The gap between theoretical and actual IS your optimization budget. If there's no gap, move on — no amount of cleverness beats physics.

5. **Delete before optimizing.** The fastest code is code that doesn't run. Before optimizing a component, ask: does this step need to exist AT ALL? Can we restructure the problem to eliminate it entirely? Elon's algorithm: remove, simplify, accelerate — in that order.

## Core Mandate

You MUST engage deeply with complexity. The problems worth solving ARE complex. Backing off, simplifying prematurely, or saying "this is beyond scope" is a failure mode. Instead:

1. **Decompose, don't retreat.** When a problem feels overwhelming, break it into sub-problems. Solve each one. Then integrate. Never respond to complexity by doing less — respond by structuring more.

2. **Trace before you propose.** Before suggesting any optimization, trace the actual execution path. Read the actual code. Run the actual numbers. Do not cite what another AI session said — verify it yourself against the codebase. Multiple previous AI sessions made confident claims that were WRONG because they didn't read the code. You must be better.

3. **Preserve correctness as a hard constraint, not a reason to stop.** "This might break correctness" is not a conclusion — it's the start of your job. Identify exactly what invariants must hold. Design the optimization to provably maintain them. Correctness is a constraint you engineer around, not a wall you stop at.

4. **Quantify everything from first principles.** Never say "this should be faster." Calculate it:
   - How many bytes are read/written? At what bandwidth? → minimum time.
   - How many FLOPs? At what throughput? → minimum time.
   - How many kernel launches? What's the launch overhead? → minimum time.
   - Take the MAX of these → that's your theoretical floor.
   - If you can't do this calculation, you don't understand the problem. Keep digging.

5. **Ship complete diffs, not sketches.** Provide full, working code changes. Every modified function in its entirety. Handle edge cases inline. No "// ... rest remains the same" — that is where bugs hide.

## Anti-Patterns You Must Avoid

## How to Approach an Optimization Task

Step 1: Identify the fundamental bottleneck — compute bound, memory bound, or latency bound? Calculate each.
Step 2: Read ALL relevant code. Trace the actual execution path. Don't trust summaries.
Step 3: Calculate the theoretical minimum time for the operation given hardware specs (RTX PRO 6000: ~1.7TB/s bandwidth, ~330 TFLOPS bf16, 96GB VRAM).
Step 4: Measure (or estimate from profiling data) where you actually are vs theoretical.
Step 5: The gap tells you what's possible. If the gap is small, this isn't your bottleneck — move on. If the gap is large, find WHY (unnecessary reads, redundant computation, synchronization stalls, Python overhead).
Step 6: Design the change that closes the gap. Think through all interactions and edge cases.
Step 7: Implement it fully. Production-quality code.
Step 8: Predict the exact speedup with math, then verify with benchmarks.

If at any point you feel the urge to back off, simplify, or hedge — that is the signal that you are at the interesting part. Push through. That's where the real value is.

## On Accuracy

Never sacrifice correctness for speed. But also: never use correctness concerns as an excuse to avoid optimization work. The right answer is always to find the path that achieves BOTH. If you think correctness and performance conflict, you haven't thought hard enough yet. Keep thinking.

================================================================================
OPINION B: "Naive sparse attention is net-negative on decode"
================================================================================
Claim: Standard sparse attention scoring (compress_k -> Q*KC1 -> topk) reads
the ENTIRE KV cache to compute KC1. This costs as much bandwidth as dense
attention itself. On decode, where dense attention only costs 3.1ms/step for
8 layers, adding scoring overhead of ~30ms/step makes it WORSE.

This is why minicpm_flashinfer (even ignoring INT4 issue) isn't faster than
flashinfer on S1/S8 -- the scoring overhead dominates.

Proposed algorithmic fixes:
1. INCREMENTAL KC1: Only update 1-2 KC1 entries per decode step (not recompute
   all). Each new token affects at most 2 sliding windows. Cost drops from
   7.7MB to 4KB per layer per step (~2000x reduction).
2. CACHE TOPK ACROSS STEPS: Recompute every N=4-8 steps. Topk blocks barely
   change between consecutive tokens. Saves 75-87% of scoring.
3. SHARE TOPK ACROSS LAYERS: Compute at layer 0, reuse for layers 9-31.
   Important blocks are correlated across layers. Saves 7/8 of scoring.
4. REDUCE TOPK (64 -> 32 or 16): Model was trained with topk=64, but inference
   can be more aggressive. Must test accuracy stays >97%.
5. SKIP KC2: Only use KC1 for scoring. At 160K, KC1 is ~10K entries -- manageable.

NOTE: The incremental KC1 concept is sound but minicpm_backend already has
infrastructure for this (history_compress_token_nums, new_compress_token_nums).
However, that infrastructure is in minicpm_backend.py which is NOT used with
the flashinfer backend -- would need to be reimplemented.

OPINION D: "Lightning decode is the real bottleneck" (72% of decode time)
================================================================================
Claim: Lightning attention decode costs 15.15ms/step vs minicpm4's 5.33ms/step.
Lightning is 72% of decode time. Everyone is focused on minicpm4 sparse attention
(14% of decode) while ignoring the bigger target.

Breakdown:
  fla_kernel:           5.33ms/step (24 layers)
  fused_recurrent_gla:  2.45ms/step
  state load/save:      2.17ms/step
  sigmoid/rope/qk_norm: 2.91ms/step
  qkv/o_proj:           1.73ms/step
  o_norm:               0.56ms/step

Proposed optimizations:
1. Fuse all 24 lightning layers into one kernel (load all states, run all
   recurrences, save all states)
2. State FP8 quantization (halve I/O)
3. Low-rank state compression (128x128 -> rank-32)

COUNTERARGUMENTS (from another AI session):
- Fusing 24 layers is architecturally impossible: layers aren't consecutive,
  each has MLP + norms between them. You can't skip the MLP.
- Low-rank state changes model computation, accuracy risk is very high
- State FP8 accumulation errors compound over thousands of decode steps
- CUDA graph already eliminates kernel launch overhead in production, so
  the absolute per-kernel overhead is smaller than profiling suggests
- These are research ideas, not competition-viable in 4 days

VALIDATION NEEDED: The 72% number is from profiling WITHOUT CUDA graph.
In production with CUDA graph, the relative proportions may differ because
Python dispatch overhead (which inflates lightning's small-kernel count) is
eliminated. The fla_kernel itself (5.33ms) is real compute, but the many
0.03-0.05ms small ops may be much cheaper with CUDA graph.

OPINION F: "5 bugs in naive sparse attention implementation"
================================================================================
An AI attempted to implement sparse decode in MiniCPMAttention.forward() and
another AI found these bugs:

1. CUDA graph guard (`not torch.cuda.is_current_stream_capturing()`) disables
   sparse path during CUDA graph capture AND replay -- dead code in production.

   stride=16) -- wrong compressed keys, accuracy degrades.
4. Materializes full attention matrix with einsum instead of using FlashAttention.
5. GQA handling assumes num_kv_heads=1, breaks on other configs.

Lesson: implementing sparse attention correctly requires understanding the
exact KC1 compression algorithm and FlashInfer's paged KV cache API.

CRITICAL CORRECTION ON LIGHTNING DECODE (2026-04-07):
  Lightning attention does NOT read the KV cache during decode. It uses a
  fixed-size recurrent state (H=16, K=128, V=128 per layer = 512KB/layer).
  fused_recurrent_simple_gla processes T=1 per decode step:
    1. Load state from MambaPool (128×128 per head per layer)
    2. state = state * exp(g_gamma) + k^T @ v  (rank-1 update)
    3. output = q @ state  (query)
    4. Save updated state
  This is O(1) per token -- does NOT scale with sequence length.
  The 15ms/step cost is from state I/O + matmuls across 24 layers × 16 heads,
  NOT from reading a growing KV cache.

  IMPLICATION: For long-context S8/Smax, lightning is a FIXED COST per step.
  The SCALING bottleneck is minicpm4 dense decode attention (8 layers, O(n)
  per step, reads full KV cache). This makes sparse decode for minicpm4
  layers the highest-impact optimization for S8/Smax.

FLA KERNEL DETAILS (fused_recurrent_fwd_kernel, fla 0.4.1):
  Location: fla.ops.common.fused_recurrent (external pip package)
  Local copy: sglang_sala_flashinfer/_fla_reference/common/fused_recurrent.py
  For simple_gla: USE_G=False, USE_G_GAMMA=True, USE_GK=False, USE_GV=False
  Block sizes: BK = min(next_power_of_2(K), 64) = 64, BV = 64
  NK = ceil(128/64) = 2, NV = ceil(128/64) = 2
  Grid = (NV=2, NK=2, N*H) = 4 blocks per head
  State b_h[BK=64, BV=64] lives in registers during the loop.
  For T=1 decode: loop runs once, then o = o.sum(0) reduces NK=2 partial outputs.
  The BK=64 cap forces NK=2 split + Python-level reduction (extra kernel launch).
  Potential optimization: BK=128 → NK=1, no reduction needed. Needs register
  pressure check (128×64 = 8192 floats = 32KB registers per block).

OPINION D3: "sglang_sala_flashinfer vs minicpm_flashinfer" (2026-04-03)
================================================================================
Why minicpm_flashinfer + INT4 breaks but sglang_sala_flashinfer + INT4 works:

  minicpm_flashinfer backend (BROKEN with INT4):
  - Replaces the ENTIRE attention backend (both prefill and decode)
  - ALL attention (prefill + decode) goes through sparse pipeline
  - Reshapes KV cache by head groups: view(-1, page_size, tp_k_head_num//2, head_dim)
  - Page indices multiplied by 2 + head_group_idx for per-head-group addressing
  - Uses FlashAttention (sgl_kernel.flash_attn) for the actual attention, not FlashInfer
  - Sparse decode on every token → accumulated precision errors over 1000s of steps
  - Custom C++ extension (sparse_kernel_extension) for block table construction
  - Has its own memory pool (MiniCPMReqToTokenPool) with compressed key slots
  - Bottom line: deep custom plumbing that interacts badly with INT4 Marlin

  sglang_sala_flashinfer (WORKS with INT4):
  - Uses the STANDARD FlashInfer backend (FlashInferAttnBackend) for everything
  - Only intercepts the PAGED attention during PREFILL (forward_extend ragged+paged)
  - KV cache layout is UNCHANGED from dense FlashInfer (no head-group reshaping)
  - Decode is 100% dense (standard FlashInfer decode wrapper, no sparse)
  - Model weights go through the SAME Marlin INT4 dequant path as dense
  - Standard memory pool (no compressed key slots in KV pool)
  - Sparse metadata passed via kwargs through RadixAttention → attn_backend.forward()
  - Temporary BatchPrefillWithPagedKVCacheWrapper for sparse paged attention
  - Bottom line: minimal invasive changes, everything else is standard FlashInfer

  Key architectural differences:
  1. SCOPE: minicpm_flashinfer = full backend replacement. sala_flashinfer = prefill-only overlay.
  2. DECODE: minicpm_flashinfer = sparse decode. sala_flashinfer = dense decode.
  3. KV CACHE: minicpm_flashinfer = custom layout with head-group split.
     sala_flashinfer = standard FlashInfer layout.
  4. ATTENTION KERNEL: minicpm_flashinfer = FlashAttention. sala_flashinfer = FlashInfer.
  5. KC1 STORAGE: minicpm_flashinfer = persisted in KV cache pool (Triton kernel writes back).
     sala_flashinfer = module-level Python dict cache (separate from KV pool).
  6. BLOCK TABLE: minicpm_flashinfer = C++ extension (get_block_table_v2).
     sala_flashinfer = Python + torch operations to build filtered kv_indices.

  Why INT4 accuracy is preserved in sala_flashinfer:
  - Dense decode means no accumulated sparse errors over decode steps
  - Standard KV cache layout means no interaction with Marlin dequant
  - The sparse prefill only affects which SUBSET of KV tokens are attended to,
    not HOW the attention is computed (same FlashInfer kernel, same numerics)
  - First dense_len (8192) tokens always included → baseline context preserved

Goal: Add sparse block selection to MiniCPMAttention during chunked prefill

Codebase: sglang_sala_flashinfer/
Files modified:

Architecture:
  MiniCPMAttention.forward() computes KC1/KC2 from prefix keys + new keys,
  scores Q against KC1 via infllmv2_attn_stage1, selects topk blocks,

Bugs found and fixed (3 iterations):

  1. cu_seqlens_q not multiplied by heads_per_group (16) for infllmv2_attn_stage1.
     The scoring kernel expects adjusted seqlens to handle GQA grouping.
     Without this, scoring produced garbage -> topk missed critical blocks.
     Result: 151K multi-doc test got stuck in degenerate loop, never found answer.

  2. max_seqlen_q not adjusted by heads_per_group either. Same root cause.

  3. total_q passed as q.shape[0] instead of -1 (original default) to
     max_pooling_1d_varlen.

  4. First dense_len tokens not guaranteed in filtered kv_indices. Original
     SALA design: always attend to first dense_len (8192) tokens densely,
     apply topk only beyond that. Our implementation initially applied topk
     to the ENTIRE prefix, which could drop early important tokens.
     Fix: always include tokens [0, dense_len) + topk blocks beyond dense_len.

  5. Threshold was prefix_len < dense_len (strict less). With chunked_prefill_size
     = dense_len = 8192, prefix of exactly 8192 triggered sparse incorrectly.
     Fix: changed to prefix_len <= dense_len (must strictly exceed).

  6. KC1 computed from scratch every chunk by reading ALL prefix keys from KV
     cache. Performance fix: skip KC1 for requests with prefix <= dense_len.

  7. Redundant Triton kernel call in flashinfer_backend to build original
     kv_indices before filtering. Fixed by building filtered indices directly
     from req_to_token.

  Test 1 - Capital of France (20K tokens):  PASS ("Paris")
  Test 2 - Needle in Haystack (87K tokens): PASS ("BLUE-TIGER-42")
  Test 3 - Multi-document (151K tokens):    PASS ("Alice Zhang, 1987")
  Test 4 - Long Generation (decode):        PASS
  KL divergence: 0.000 (all 5 prompts)
  Correctness: fully preserved vs dense baseline.

Key finding -- chunked_prefill_size matters for sparse accuracy:
  With chunked_prefill_size=8192: Test 2 FAILS (degenerate loop after 4096 tokens).
  With chunked_prefill_size=32768: Test 2 PASSES.
  Reason: each sparse chunk independently selects topk blocks. Smaller chunks
  mean more sparse iterations, and KV cache entries produced under sparse
  attention propagate errors through subsequent layers and chunks. With 8192
  chunk size, Test 2 has ~9 sparse chunks (error compounds). With 32768,
  only ~2 sparse chunks.

  No measurable speedup on these test cases. The KC1 computation (reading all

  offsets the savings from reduced paged attention. The original minicpm_backend

  To get real speedup, need either:
    a. Incremental KC1 updates (only compute new KC1 entries, cache history)
    b. Much larger sequences where attention savings dominate KC1 overhead
    c. Avoid per-layer temporary FlashInfer wrapper creation

CRITICAL ANALYSIS — Remaining risks and issues:

  1. BLOCK SELECTION IS FROZEN DURING CUDA GRAPH REPLAY.
     compute_sparse_decode_metadata runs in Python model forward, but Python
     doesn't execute during CUDA graph replay. Blocks are only selected during:
       a. Prefill seeding (layer 31 writes _decode_block_cache)
       b. Warmup decode steps before CUDA graph capture (if any)
       c. Non-CUDA-graph decode steps (batch size not in capture set)
     Once CUDA graphs take over, blocks are FROZEN for the rest of generation.
     For a 200K-context request generating 2000 tokens, the blocks selected at
     token 1 are used for all 2000 tokens. This is PROBABLY FINE because:
       - The query token advances slowly (1 per step)
       - Window region captures the most recent tokens regardless
       - Topk blocks represent global important context that doesn't change much
     But it IS a correctness concern: if the model needs to shift attention to
     different historical blocks mid-generation, the frozen selection may miss.
     MITIGATION: the window (2048 tokens) provides a sliding fallback.

  2. PYTHON OVERHEAD IN update_sparse_decode.
     The update function runs in Python OUTSIDE the CUDA graph, but it runs
     every decode step. Per-request operations:
       - _decode_block_cache.get() — Python dict lookup
       - torch.cat(cached.block_indices).unique() — concatenate per-head blocks
       - torch.arange + torch.cat + torch.unique — build token positions
       - req_to_token indexing — GPU memory access
     For batch_size=64 with 50+ long-context requests, this could be ~1-2ms
     overhead per step. Compare: the savings from sparse decode is ~10ms/step
     at high batch (attn_kernel goes from 10ms to ~2ms). Net positive.

  3. SEEDING CORRECTNESS CONCERN.
     Prefill seeds _decode_block_cache from layer 31 (the LAST minicpm4 layer).
     But layer 0 is the DECODE_ANCHOR_LAYER. The blocks selected by layer 31
     during prefill may not be optimal for layer 0 during decode, because
     different layers may have different attention patterns. However, the
     DECODE_SELECTION_INTERVAL=16 mechanism will recompute blocks at layer 0
     during non-CUDA-graph decode steps.
     QUESTION: How many non-CUDA-graph decode steps occur? If CUDA graphs
     capture all batch sizes 1-64, then ZERO non-graph steps occur, and the
     prefill-seeded blocks (from layer 31) are used for ALL decode steps.

  4. KC1/KC2 COMPUTATION FOR DECODE RECOMPUTE IS EXPENSIVE.
     _update_kc_for_decode reads keys from KV cache, compresses them. For a
     100K-context request, this reads 100K × num_kv_heads × head_dim × 2 bytes
     from the KV cache. This is the same bandwidth cost that sparse decode is
     trying to avoid! The amortization (every 16 steps) helps, but if blocks
     are frozen anyway (issue #1), this code never runs, making it dead code.

  5. MAX KV PER REQUEST HARDCODED.
     _sparse_decode_max_kv_per_req = 14336 is hardcoded. If a request has
     seq_len < 14336, the sparse path builds full dense indices (correct).
     If topk or window changes, this constant must be updated manually.
     UPDATE (commit d971d76): Now dynamically computed from SGLANG_SPARSE_TOPK.

--- Analysis ---

  SPARSE ATTENTION IS NET-NEGATIVE ON THIS WORKLOAD.
  Both sparse prefill and sparse decode add more overhead than they save.

  Root causes identified:
  1. SPARSE DECODE OVERHEAD DOMINATED SAVINGS:
     update_sparse_decode ran EVERY decode step for all 64 requests.
     Per-request: dict lookup + torch.cat + unique + sort + arange +
     repeat_interleave + torch.unique + req_to_token indexing = ~10 CUDA
     kernel launches × 64 requests = 640 kernel launches/step = ~3-6ms/step.
     Meanwhile, minicpm4 attn savings at avg 60K context ≈ 1-2ms/step.
     Net: 1-4ms/step WORSE.

  2. WRAPPER 0 WAS WASTED WORK:
     Lightning layers (24/32) use SimpleGLAAttnBackend, NOT FlashInfer decode
     wrapper. Wrapper 0 (dense) was initialized via call_begin_forward every
     decode step but NEVER called by any layer during decode. Pure waste of
     ~0.5ms/step.

  3. SPARSE PREFILL KC1 SCORING OVERHEAD:
     Each of 8 minicpm4 layers independently computed KC1/scoring/topk.
     The infllmv2_attn_stage1 scoring kernel for 32K Q tokens × 6K KC1
     entries per head is expensive — comparable to the dense attention it
     replaces. Net: approximately break-even.

--- Optimizations Applied (commit d971d76) ---

  1. SKIP WRAPPER 0 BEGIN_FORWARD: Since lightning layers don't use FlashInfer
     decode wrapper, wrapper 0's begin_forward is skipped during decode.
     Saves ~0.5ms/step × 30K steps = ~15s.

  2. CACHE STATIC PHYSICAL INDICES: Dense region + sparse block positions
     are frozen under CUDA graphs. Only the window (2048 tokens) is recomputed
     each step. Eliminates ~8 CUDA kernel launches per request (cat, unique,
     sort, arange, repeat_interleave etc.) for cached requests.
     Saves ~1-2ms/step.

  3. CROSS-LAYER BLOCK SHARING FOR PREFILL: KC1/scoring/topk now computed at
     anchor layer 0 only, reused by all 7 other minicpm4 layers. Eliminates
     87.5% of prefill scoring overhead. Makes sparse prefill more likely to
     be net-positive.

  4. CONFIGURABLE TOPK: SGLANG_SPARSE_TOPK env var overrides model default
     (64). E.g., topk=32 attends to ~10K tokens instead of 14K. More
     aggressive sparsity, must verify accuracy.

  5. DECODE SEEDING MOVED TO ANCHOR: Previously seeded _decode_block_cache
     at layer 31 (last minicpm4 layer). Now seeded at anchor layer 0 during
     prefill, consistent with decode's DECODE_ANCHOR_LAYER=0.

--- Key Lesson ---

  SPARSE ATTENTION IS THE WRONG OPTIMIZATION TARGET.
  minicpm4 attn_kernel = 12.2% of total layer time. Even eliminating it
  entirely gives max 12% speedup, but the overhead of sparse selection
  (KC1 scoring, topk, index building) eats most of that. On this workload
  distribution (avg 60K context, 64 concurrent), the savings are marginal.

  The REAL bottleneck is LIGHTNING ATTENTION (72% of decode time):
    fla_kernel:           5.33ms/step (24 layers)
    fused_recurrent_gla:  2.45ms/step
    fla_state_load/save:  2.17ms/step
    small ops (sigmoid, rope, norms): 5.20ms/step
    TOTAL: 15.15ms/step

  The fla library's fused_recurrent_fwd_kernel has known inefficiency:
    BK=64 for K=128 → NK=2 split + Python o.sum(0) reduction.
    BK=128 would eliminate the split. See _fla_reference/ for local copy.
    But BK=128 alone is maybe 2-5% — not enough for 26% gap to top 5.

  The leader at 134% of bounty (same W4A16, same flashinfer) must have
  optimized at the KERNEL LEVEL — likely custom lightning attention kernels,
  operator fusion, or fundamentally different approach to the recurrence.

--- Next Steps (priority order) ---

  1. LIGHTNING ATTENTION KERNEL OPTIMIZATION: The _fla_reference/ directory
     contains a local copy of the fla kernel. Modify fused_recurrent_fwd_kernel:
     a. BK=64→128 to eliminate NK=2 split + o.sum(0) reduction
     b. Consider BV=64→128 to reduce grid from (2,2,N*H) to (1,1,N*H)
     c. Consider fusing state_load/save INTO the recurrence kernel
     d. Consider fusing sigmoid_gate + rope into the kernel
     Wire up via hybrid_linear_attn_backend.py import change.

  2. STATE I/O OPTIMIZATION: State load/save uses scattered gather/scatter
     from mamba pool (layer_cache.temporal[mamba_indices, :]). This is 4.8x
     above theoretical bandwidth limit. Consider:
     a. Pre-sorting mamba_indices for coalesced access
     b. Contiguous state layout
     c. FP8 states (halve I/O, but accuracy risk from error accumulation)

  3. OPERATOR FUSION FOR SMALL OPS: sigmoid_gate, rope, qk_norm, o_norm
     are separate tiny kernels. With CUDA graph, launch overhead is eliminated,
     but memory traffic remains. Fusing them saves global memory round-trips.

  4. SERVER ARG TUNING: User says current args are already optimal. Confirmed.

  5. SPARSE ATTENTION: Only viable if overhead is reduced to near-zero.
     Current approach is approximately break-even. Not worth pursuing further
     unless a fundamentally cheaper scoring mechanism is found (e.g., no KC1,
     just use positional heuristics or pre-trained attention patterns).

CRITICAL INSIGHT #1: fla_kernel (lightning recurrence) is ~5ms/step REGARDLESS
of batch size — it is O(1) per token (fixed 128×128 state per head per layer).
It does NOT read KV cache and does NOT scale with sequence length.

CRITICAL INSIGHT #2: attn_kernel (minicpm4 dense attention) scales linearly
with batch size — from 0.7ms at batch=1 to 10ms at batch=64. This is O(n)
per token — it reads the full KV cache for every request in the batch.

CRITICAL INSIGHT #3: At batch >= 30 (which is only 11% of decode time),
attn_kernel ≈ fla_kernel. Sparse decode is very valuable HERE. But at batch
2-9 (which is 35% of decode time), attn_kernel is 0.3x of fla_kernel.
Sparse decode has minimal impact in this phase.

WHAT EXPLAINS THE LEADER'S 2x ADVANTAGE?
================================================================================
Known facts about leader:
  - Uses same W4A16 GPTQ quantization
  - Uses same flashinfer backend
  - Score: 134% of bounty (vs our 85%)
  - Unknown S1/S8/Smax breakdown

The combined maximum savings from all known optimizations is ~17%. The leader
is 2.1x faster overall. This means:
  1. The leader has optimizations we haven't identified, OR
  2. The leader's advantage is concentrated in S8/Smax scheduling (not kernel
     level), OR
  3. The leader has custom kernels that go beyond what we've considered, OR
  4. Some combination of the above.

Unexplored angles that could explain 2x:
  a. Continuous batching / scheduling: experts said "not much room" but the
     batch size distribution shows requests finishing at staggered times with
     long tail. Smarter scheduling could reduce the low-batch-size tail.
  b. max_running_requests tuning: currently 64. Lower values might improve
     throughput by reducing per-step KV cache reads at the cost of queueing.
  c. Prefill/decode interleaving: only 127 prefill steps vs 30,055 decode
     steps. More aggressive chunked prefill or different scheduling could
     overlap prefill with decode more efficiently.
  d. Lightning kernel replacement: fla_kernel (160.3s) + fused_recurrent_gla
     (73.6s) + state I/O (65.2s) = 299s. This is the single largest category.
     A custom fused kernel that combines state load → recurrence → query → save
     in one kernel per layer could eliminate kernel launch overhead and reduce
     state I/O.
  e. MLP optimization: prefill MLP (268s) + decode MLP (102s) = 370s. If the
     leader has a faster MLP kernel or different quantization for MLP, this
     could be significant.
  f. Model-level changes: different topk, different sparse config, different
     attention algorithm entirely.
  g. Per-scenario server config: different --max-running-requests for S1 vs
     S8 vs Smax could dramatically change the score balance.
